## 1. What is this product, in my own words

It is a pack of ten skills for Claude Code — prompt-side workflow modules — plus one shared rulebook they all load. Together they impose spec-driven discipline on agent coding: when you tell the agent a wish in plain conversation ("the report page needs a date filter"), the pack routes that sentence into a living spec document, has the spec reviewed by a formal-verification-style pass, derives tests from the spec, writes the code until green, and commits code and documents together. The enforcement layer is not the model: four Python scripts on the git pre-push hook (mirrored in CI) refuse the push when the shipped code and its documents disagree — surfaces without spec anchors, changes without tests, duplicated anchors, and so on. The pitch is that other frameworks ask a model to verify the spec was followed, and a model can lie or drift; here the final gate is mechanical.

## 2. How I would adopt it, as I understood the page

1. In Claude Code, run the two plugin lines: `/plugin marketplace add happysasha18/live-spec` then `/plugin install live-spec@live-spec`. (Alternative: clone the repo and run `./install.sh`, which copies skills into `~/.claude/skills/`.)
2. Open my project in Claude Code and say, in plain words, "attach live-spec to this project" (or "found a new project on live-spec" in an empty directory). The pack reads my tree and runs a setup walk — `adopt/ADOPT.md` for an existing codebase — and on that path writes the first spec from what my code ships today.

5. Add the four check lines to `.git/hooks/pre-push` (listed in `scaffold/guardrails/README.md`), creating the hook file and making it executable if needed. Prerequisites: Python 3.9+, project already a git repo.
6. From then on, talk: any wish, "status", "publish".

## 6. Three questions for the author before trusting the page

1. **Which install path is canonical?** Walk me through the exact steps for a plugin-install user: after `/plugin install`, do I run `install-scaffold.sh` from `~/.claude/plugins/cache/`, or must I also clone? The Install section reads as two overlapping paths spliced together, and the scaffold clone block sits where a plugin user will run it needlessly.
2. **What do the four checks actually compare?** "A script... compares the spec to the code that shipped and refuses the push when the two disagree" is a strong claim, but the four checks described are proxies: registry completeness, anchor existence, test presence on changed files, no duplicates. A behaviour can drift from its spec sentence while every proxy stays green. Where are the red-first proofs, and what class of disagreement do the gates provably catch versus miss?
3. **Can I see a second production project?** Three projects are claimed, one named. Point me at one adopted repo that is not the pack itself — its `PRODUCT_SPEC.md`, `SURFACES.md`, the queue, a delivery report with source-tagged claims, and one refused push — so the control-and-reporting promises rest on something I can open. (And while there: define "the queue" and "the settings card" somewhere a first-time reader can find.)
