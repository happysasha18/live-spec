## What changed

Two new rules landed the night of 2026-09-02, both under `## Execution`: a closing rule (the
Director shows a delivered result and closes the checkpoint in the same step, reserving the
"needs his eye" gate for a taste call, an undecided trade-off, or a change to the definition of
correct) and an argue-first rule (writing the decision sheet is also the moment to weigh whether
the request itself is right, and a flaw the Director can see gets voiced before the checkpoint
opens). File went from 25,613 to ~26,700 bytes, still well under the tool's own 500-line guidance
(415 lines). Both rules are proven by real, independent producer runs
(`evals/director/closing-scenarios.json`, 9/9), not asserted from the prose alone — the harness this
project's own `evals/director/README.md` describes as the discipline for exactly this skill.

## Findings

1. **Frontmatter description does not name either new rule.** The `description:` line still reads
   "...call the specialists it needs, and carry it through — checkpoint, verify, close, report,"
   written before tonight's two additions. Skill-creator's own guidance treats the description as
   the primary summary a reader (or a future session deciding whether to re-read the skill) meets
   first, and it should reflect what the body actually does. **Considered and reverted, not
   folded:** a draft edit adding "voice any disagreement with the request itself before starting"
   was written and tested; it changed the file's sha256, which this project's own freshness gate
   (`tests/test_director_scenarios.py::test_closing_runs_were_recorded_against_the_skill_as_it_stands`)
   reads as "the skill changed" — triggering the same 44-producer-call re-record (35 + 9) that a
   real behavior change owes. Spending that on a metadata-only line that changes no instruction a
   producer follows is the "don't serve machinery nobody needs" standing rule in the other
   direction: paying a real re-eval for a wording label change. Left as an open, low-cost item for
   whenever `director/SKILL.md` next changes for a real reason and the re-record is already owed.
2. **Structural ordering: the two new paragraphs sit in a slightly counter-intuitive order.**
   "Closing the work closes the checkpoint in the same step, never a later one" (the *mechanical*
   step: run `checkpoint.py close`) is immediately followed by "A shown result closes the work..."
   (the *judgment* rule: when it's correct to consider work closed). Reading order would read more
   naturally with the judgment rule first (decide it's closeable) then the mechanical step (how to
   actually close it). Not folded — reordering two long paragraphs this late in a busy night's
   range is a real diff for a purely cosmetic gain, and the eval harness (which reads the whole
   file, not paragraph order) already proves the rule works regardless of its position.

No findings against the two new rules' own content, only against their presentation — both read
plainly, avoid contrast frames, and match the register the rest of `## Execution` already uses.
