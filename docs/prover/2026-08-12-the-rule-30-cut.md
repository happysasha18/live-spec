## How this record has to be committed

The record's `Range:` field cannot name the commit that carries it, and gate s is built around that.
`guardrails/check-prover-record.sh` reads the pushed range, then reduces it to the *reviewed* commits
— those touching at least one file outside `docs/prover/` — and demands the record's body contain the
base's short hash and every reviewed commit's short hash. Its own comment states the exemption: a
commit that carries the record alone is exempt, since the record cannot name the commit that first
ships it.

So the repair and this record cannot ride in one commit. A single commit carrying `NEXT_STEPS.md`,
`guardrails/rule-census.json` and this record touches files outside `docs/prover/`, which makes it a
reviewed commit, which makes the record owe its own hash. No wording of the `Range:` field escapes
that, because the gate matches hashes as substrings of the whole body and never parses the field's
prose.

Yesterday's push is the precedent, and it is the split device rather than the combined one.
`git show --name-only dfa9f57` returns one path, `docs/prover/2026-08-11-thirty-commit-range.md`. The
record rode inside the pushed range, as the coordinator recalls, but in a commit that carried the
record and nothing else — the exempt shape. The reviewed tip that record had to name was the commit
before it.

The three steps that make this push pass. Commit the prose repair on its own, `NEXT_STEPS.md` and
`guardrails/rule-census.json` and no third file. Replace `382b304` on this record's second Range
line with that commit's seven-character short hash. Then commit this record alone, and it becomes the
push tip under the exemption. Run `bash guardrails/check-prover-record.sh --push` after the second
commit to confirm; it prints the range and the reviewed count when it passes.
