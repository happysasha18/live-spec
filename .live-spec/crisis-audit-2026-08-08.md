# live-spec: кризисный диагноз и план выхода

08.08.2026, по твоему заказу от 20:45. Основа: два независимых прохода агентами — хроника недели по журналу и очереди, и замеры всего дерева свежим взглядом. Вердикт — мой. Каждую цифру можно перемерить по команде; детали даю по запросу.

## Вердикт

Проект жив, и идея продукта здравая. Болезнь в том, что система охраны качества выросла в самостоятельный организм и потребляет проект. Пакет, который должен ставить себе чужой проект, — это 7 400 строк текста скиллов; машинерия, которая его сторожит, в 7,8 раза больше. Из последних 46 задач очереди 28 обслуживают саму систему, 11 — поведение твоих сессий, и только 7 приближают продукт к постороннему пользователю. Прошедшая неделя ушла именно на это: система чинила собственные проверки, починки ломали новое, продукт стоял.

## Проблемы по рангу

**1. Система работает на себя.** 94% дерева по объёму — самонадзор: 2 502 теста, 27 барьеров перед публикацией, 103 файла проверок — на пакет из полутора десятков файлов. Каждый сбой рождает новую проверку, каждая проверка — новые задачи по её обслуживанию; за всю жизнь проекта списана одна проверка из ~130 (git-история удалений). Дерево прямо сейчас красное: два входящих сообщения обратной связи валят сборку.
Решение: бюджет на машинерию. Новая проверка входит только вместо старой. Барьеры публикации сокращаются с 27 до ~5 содержательных. Перепись срабатываний — когда каждая проверка последний раз ловила что-то реальное — решает, кого списать; списание по твоему слову.

**2. Строгость направлена на не те дефекты.** Самый обустроенный дефект в истории проекта — минутный сдвиг метки времени в чате: 22 пойманных случая, хук, барьер в коммите, 990 слов в журнале проблем. В это же время инсталлятор отдаёт наружу скиллы со 183 ссылками на файлы, которых у получателя нет, — и ни одна из 2 502 проверок этого не видит, потому что ни одна не смотрит глазами постороннего.
Решение: главным тестом проекта становится критерий чужака — посторонний человек на чистой машине ставит пакет по README без посторонней помощи и проходит первый цикл; время замеряется и публикуется как факт. Всё, что на этот критерий и на читаемость твоих отчётов не влияет, — кандидат на списание.

**3. Правила переросли исполнителя.** Свод правил, который сессия загружает до начала работы, — 45 000 токенов (замер страницы затрат, 07.08); спецификация — 704 КБ, 310 требований, 314 инвариантов. Твоё июльское наблюдение — что спустя пару запросов сессия начинает писать чушь — прямое следствие: перегруз, из-за которого правила нарушаются, создан самими правилами. До сих пор это лечили переписями и ротацией, то есть ещё одной машинерией.
Решение: правил становится меньше. Целевой размер — свод, который человек читает за один присест. Начатый срез свода правил продолжается, но с этой целью.

**4. Единственный пользователь — ты.** Вся обратная связь за жизнь проекта — от тебя и твоих трёх окон; это твой сознательный выбор до поры (проект пока не показывается наружу). Следствие для дерева всё равно действует: очередь оптимизирует поведение твоих же сессий, и день, когда проект можно показать, не приближается. Цель проекта — твоими словами от 08.08 — открытый код агентного проактивного конвейера, чтобы быть полезным.
Решение: после стабилизации головой очереди становится готовность к постороннему — прогон, где чистая машина или папка вне твоих проектов получает пакет по README и проводит одну фичу через весь конвейер; каждый затык записывается как дефект продукта.

**5. Большие работы стартуют без определения готовности.** Доска: девять расширений постановки за один вечер, 99 критериев, восемь макетов, ноль сборки. Кампания читаемости: три захода, до 18 переписываний одного текста, итог по твоей же оценке нулевой.
Решение: любая работа длиннее одной сессии открывается тремя строками — что считается готовым, бюджет, чем меряем. Без трёх строк работа не стартует.

## Судьба вчерашнего документа

Диагноз в нём в основном верен: мои независимые замеры его подтвердили. Негоден он как изделие: нечитаем, получил 8 блокирующих находок от собственного ревью, после исправлений всё ещё держит неверное число открытых задач, и его план лечит машинерию новой машинерией — продукт появляется только шестым шагом. Сохранить из него четыре вещи: файл текущего приказа с замороженными формулировками; сортировку очереди в одну страницу; перепись срабатываний проверок; правило трёх строк. Остальное в архив.

## План выхода

**Фаза 1 — остановка (1–2 дня).** Мораторий на новые правила и проверки. Дерево приводится в зелёное. Очередь из ~200 открытых задач сортируется в одну страницу: В РАБОТЕ (до трёх) / СЛЕДУЮЩИЕ (~10) / ДАЛЬНИЕ; вычёркиваешь ты.

**Фаза 2 — похудение (порядка недели).** Барьеры публикации 27 → 5. Перепись проверок, молчащие списываются по твоему слову. Свод правил режется до читаемого за присест. Инсталлятор чинится, 183 битые ссылки закрываются.

**Фаза 3 — разворот к продукту.** Критерий чужака становится главным тестом. Доска достраивается по замороженной постановке. Первый прогон внедрения на стороне.

## Что сохранить

Тезис продукта настоящий: проверка скриптом надёжнее самоотчёта модели, и README формулирует это сильно. Отдельное издание product-prover — готовый к отгрузке артефакт и доказательство, что пакет умеет рождать изделие. Единая грамматика спеки, матрицы и очереди — здравая архитектура. Это ядро. Остальное — упаковка, и ей предстоит похудеть.
