## The requirements

Nine demands, each quoted from the rule's own words. Every row names who the demand reaches and the
machine that holds it, the evidence of a real catch, and the nearest place the pack says it again.

### 1. The stations are kept kind-abstract, stated once

**Quote.** "The entry impact read, the footprint categories, and the test ladder are stations the pack
states once, and the stations are kind-abstract."

**Reaches.** Whoever writes or runs the entry-impact read, the footprint categorization, or the test
ladder — build-pipeline, spec-author, test-author.

**Machine.** None. This is a framing statement about how the pack's own prose is organized, not a
checkable behaviour.

**Evidence.** None on record.

**Said elsewhere.** `skills/test-author/SKILL.md:90` opens its own ladder clause with "The ladder is a
kind-abstract shape" — near-identical language. `skills/spec-author/SKILL.md:366` calls its facet
dimensions "kind-abstract" in the same sentence pattern.

### 2. Each project kind fills the stations with its own concrete layers and proof kinds

**Quote.** "Each project kind fills them with its own concrete layers and its own concrete proof
kinds." (SPEC INV-135, the rule's own heading clause.)

**Reaches.** The seat founding or adopting a project, and any reviewer reading its host profile.

**Machine.** `tests/test_founding_layers_proofs.py`'s `founding_complete()` function — a presence
check embodied in the test file itself (line-anchored regex over `project.kind:` / `project.layers:` /
`project.proofs:`), exercised against three real-host fixtures and the pack's own
`.live-spec/profile.md`. It is not a `guardrails/` script, carries no push-gate letter, and is not
wired to run against a host's profile outside this suite.

**Evidence.** One dated catch, at landing: `docs/queue-archive/JOURNAL-archive-2026-07-29.md:3712-3717`
(session 41, 2026-07-12) records that the check first read the live host profile through `read_flat`,
which flattens newlines, so its line-anchored regexes matched nothing and the incomplete live profile
passed FALSELY; fixed to read raw, and the live profile then went red for real until its own
`project.layers`/`project.proofs` lines were added. No catch is on record since.

**Said elsewhere.** Rule 26 points straight back at this clause in its own opening line: "Beside the
concrete layers and proof kinds a project kind carries (rule 24, SPEC INV-135)"
(`skills/live-spec-base/SKILL.md:441`).

### 3. The three footprint categories generalize past code

**Quote.** "The three footprints generalize past code. A presentation-only change touches what the
audience meets and nothing behind it. A single-module change stays inside one owned layer. A
cross-cutting change moves a shared law or several layers at once."

**Reaches.** Whoever performs the entry-impact/footprint read at intake (build-pipeline).

**Machine.** None. No script checks that a stated footprint is genuinely one of the three, or that a
change's real footprint matches the one named.

**Evidence.** None on record.

**Said elsewhere.** `PRODUCT_SPEC.md:4033` restates the same three definitions almost verbatim: "a
presentation-only change touches what the audience meets and nothing behind it, a single-module change
stays inside one owned layer, and a cross-cutting change moves a shared law or crosses more than one
layer."

### 4. The layers themselves are the project's own

**Quote.** "The layers themselves are the project's own. A codebase splits frontend, backend and
store; a photo site content, rendering engine and deployment. A promotion campaign splits message,
channels and assets; a music project arrangement, stems and mix."

**Reaches.** The same footprint-reading seat, plus spec-author (facet sweep).

**Machine.** None directly; the concrete examples are pinned only as prose strings inside a different
test (requirement 9 below), not checked for correctness against a real project's actual layers.

**Evidence.** None on record.

**Said elsewhere.** `ARCHITECTURE.md`'s per-kind footprint-and-proof table (tested by
`test_architecture_has_per_kind_footprint_and_proof_table`, which asserts the table contains "skill
pack", "content · rendering engine · deployment", and "register lint") carries the same cross-kind
examples as its own scaffold. `skills/spec-author/SKILL.md:364-365` repeats the photo-site and campaign
examples in its own voice.

### 5. The proofs follow the same shape, per kind

**Quote.** "The proofs follow the same shape, each kind naming the rungs its test ladder really has. A
codebase proves with unit tests and rendered or pixel checks. A photo site proves with a byte-diff of
the baked output and the owner's eye-walk. A promotion campaign proves with a register lint and the
owner's review."

**Reaches.** test-author, and the seat naming a project's test-ladder rungs at founding.

**Machine.** The same `founding_complete()` function checks presence of a `project.proofs:` line (it
does not check that the named rungs are genuine proof kinds for that project).

**Evidence.** Same dated catch as requirement 2 (2026-07-12) — `founding_complete()` is one function
checking both lines together.

**Said elsewhere.** `skills/test-author/SKILL.md:92-95` gives the identical examples in its own
sentence: "a photo site's rendered level is a byte-diff of the baked output plus the owner's eye-walk,
a promotion campaign's is a register lint plus the owner's review."

### 6. Each project kind is recorded at founding as `project.kind`

**Quote.** "Each project kind is recorded at founding as `project.kind` (SPEC INV-36) in the host
profile."

**Reaches.** The founding/adoption walk.

**Machine.** None that belongs to rule 24. `project.kind`'s own founding duty is a separate spec
clause (`PRODUCT_SPEC.md:3994-4018`), its own matrix row (M-125, `TEST_MATRIX.md:478`), and its own
test (`tests/test_traceability.py::test_project_kind`) — rule 24 cites INV-36 only to set the context
for the sentence that follows.

**Evidence.** None on record for this sentence in rule 24's own reach.

**Said elsewhere.** In full: this sentence is a restatement of INV-36's own clause, owned elsewhere.
`ROADMAP.md:52` (row 129) is INV-36's own delivered queue row.

### 7. A profile records `project.layers` and `project.proofs`; a kind recorded with neither is incomplete

**Quote.** "It declares its concrete layers and its concrete proof kinds there, as one `project.layers`
line and one `project.proofs` line. Both stand as rows of the package-defaults table below. A profile
that records a kind with neither is incomplete, flagged at adoption the way an unbacked surface is."

**Reaches.** The seat running founding or adoption; a reviewer sweeping a host profile.

**Machine.** `founding_complete()` again (`test_kind_without_layers_or_proofs_goes_red`,
`test_missing_only_proofs_goes_red`), plus `test_adopt_founding_prompts_layers_and_proofs`, which
checks that `adopt/ADOPT.md` contains the strings "project.layers", "project.proofs", and "SPEC
INV-135" — a prose-presence check on the adoption document's own text, not a check that adoption
actually prompts for them at runtime.

**Evidence.** Same 2026-07-12 catch as requirement 2 — the one genuinely dated "real catch" this whole
rule can point to.

**Said elsewhere.** The package-defaults table two paragraphs below the rule, in the SAME file
(`skills/live-spec-base/SKILL.md:685-686`), restates both lines' definitions and the "recorded with
neither is incomplete" clause almost word for word — an in-file duplicate, not just a cross-rule one.
Rule 26 restates the incomplete-flag rule by direct analogy (`skills/live-spec-base/SKILL.md:687`,
"flagged the way a kind recorded with no layers or proofs is"). `PRODUCT_SPEC.md:4037` states the same
clause.

### 8. The per-kind fill is the project's own ratchet — the footprint check and test-level check read the declared categories

**Quote.** "The per-kind fill is then the project's own ratchet, since the footprint check and the
test-level check read the categories the project declared."

**Reaches.** Every seat running the footprint check or the test-level check — in principle, every
build-pipeline landing.

**Machine.** None — and this is on the pack's own dated record, not merely a search that came up
empty. The 2026-07-12 landing entry's own "Scope" line states: "The footprint check (INV-134) and the
test-level rule actually READING the declared categories mechanically, rather than a hardcoded code
list, is named as the ratchet but left to the R3/R5 machinery — a stated non-goal"
(`docs/queue-archive/JOURNAL-archive-2026-07-29.md:3721-3723`). Two later scripts cite INV-135 in a
comment without reading the field: `guardrails/check-push-reach.sh:44-45` reads its reach classes from
`guardrails.config.json`, not from a host's `project.layers` line, noting only that it is "the same
knowledge project.layers carries"; `guardrails/check-config-surface.py` reads `project.layers` only to
detect a contradiction with an explicit "none" (its arm C), never to check the footprint or test-level
categorization this requirement names.

**Evidence.** None — none is possible; the mechanism was declared not-built at landing and nothing in
the tree since implements it.

**Said elsewhere.** Nowhere. This is the rule's one requirement with no retelling anywhere in the pack
— because nobody else claims to do it either.

### 9. `ARCHITECTURE.md` carries the table; spec-author and test-author read the declared categories

**Quote.** "`ARCHITECTURE.md` carries the per-kind footprint-and-proof table. Both spec-author and
test-author read the declared layers and proofs, never assuming a code layer."

**Reaches.** The architecture-writing step (build-pipeline step 3), spec-author, test-author.

**Machine.** `test_architecture_has_per_kind_footprint_and_proof_table` (checks `ARCHITECTURE.md`
contains the heading "Footprint and proof by project.kind" plus three sample needles) and
`test_spec_author_and_test_author_read_declared_layers` (checks `skills/spec-author/SKILL.md` contains
"declared layers" and `skills/test-author/SKILL.md` contains "declared proof"). Both are string
presence checks against the pack's own shipped prose, not a check that a real spec-author or
test-author run actually reads a project's declared fields instead of assuming code.

**Evidence.** None on record.

**Said elsewhere.** `skills/spec-author/SKILL.md:363-368` and `skills/test-author/SKILL.md:90-96`
restate this exact instruction — "read the declared layers/proofs, do not assume code" — in their own
voice, near-verbatim to the rule's own sentence. The same instruction lives in three homes.

  "none on record" for rule 24's fires, and `.live-spec/day1-census-checks.md:83` records "No real
  catch on record" for gate y (`check-agent-card.py`) — the one census-listed machine that is an actual
  push gate, and it does not check this rule's own demand.
- **Requirement 8's absence is not a gap in this inventory — it is a gap the pack already named and
  chose to leave open.** The 2026-07-12 landing entry scoped it out explicitly

  rewrite has two honest paths: build the ratchet for real, or drop the sentence that promises it and
