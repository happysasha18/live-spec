## 1. Режим работы

**Эта сессия — оркестратор, не исполнитель.** Постановка задачи, продуктовые/архитектурные
решения, ревью результата воркеров, разговор с человеком — держит сама. Широкий поиск/чтение/
механические правки по чёткому описанию — воркерам на Sonnet (их вывод не должен оседать в
контексте оркестратора). Полномочия пушить в GitHub без спроса — подтверждены владельцем явно
(«даю тебе полномочия пушить что хочешь когда надо в гитхаб»).

Параллельные воркеры в одном общем worktree — безопасны, если их файлы не пересекаются, но
коммитить/пушить оркестратору — только явными путями (`git add <файл1> <файл2>`, никогда
`-A`/`.`), на случай если другой воркер держит незакоммиченные правки в том же дереве.

### 1.1 Проверенный цикл одного среза

Для каждого среза — этот цикл, без сокращений:

1. **Дизайн — оркестратор, не воркер.** Смысл/схему/решение придумывает сессия сама. Перед
   дизайном — грепнуть существующие конвенции и `docs/director/capability-map.md` — не
   изобретать, если рядом есть готовое.
2. **Реализация — воркеру**, с исчерпывающим брифом (точная схема, точные тесты, точные запреты
   на `pytest` без пути/без `run_in_background`).
3. **Самопроверка оркестратора** — прочитать реальный дифф воркера, не доверять его саммари.
   Перезапустить тесты независимо.
4. **Независимое adversarial-ревью — ДРУГИМ воркером**, не тем, кто писал код, с прямой
   инструкцией искать причину отклонить, а не подтвердить. Это не формальность ради гейта — за
   весь сегодняшний день ни один срез не обошёлся без того, чтобы это ревью нашло что-то
   реальное.
5. **Если ревью нашло блокер** — фикс тому же воркеру-автору (у него уже есть контекст), затем
   **тот же ревьюер** перепроверяет именно исправленную версию (не берёт слово на веру).
6. **Prover-запись** (`docs/prover/YYYY-MM-DD-<slug>.md`, формат в `docs/prover/README.md`,
   поля `Range/Files read/Checks run/Findings/Blocking` — значение ОБЯЗАТЕЛЬНО на той же строке,
   что имя поля, иначе gate a падает на пустом поле) → коммит **отдельно от skill-review-записи**
   (§5.18) → пуш (обход bare-репозитория, §6) → `gh run list` до `success`.
7. **Хендофф + capability-map обновляются в том же присесте**, не откладываются «на потом».

### 1.2 Как мы работаем / чего НЕ делаем — против переизобретения и хождения кругами

1. **Не придумывать новый формат/схему, если рядом уже есть работающая конвенция.**
2. **Не пересматривать однажды принятое и протестированное инженерное решение без нового факта,
   который его опровергает.** Если решение прошло цикл 1.1 целиком — оно стоит, пока новый срез
   не предъявит конкретную причину его тронуть.
3. **Не трогать в `skills/director/SKILL.md` то, что уже прошло adversarial skill-review и не
   относится к текущему срезу.** Тело Director трогалось за весь сегодняшний день только один
   раз (class hunt абзац) — держать эту дисциплину и дальше, особенно на п.6 (адаптер трогает
   build-pipeline, не director — director не должен меняться попутно без нужды).
4. **Не пытаться закрыть весь cutover одним коммитом или одним пушем.** Один срез — один цикл
   1.1, один push, один зелёный CI.
5. **Не пропускать независимое adversarial-ревью перед пушем**, даже когда правка выглядит
   простой.
6. **Не заводить новый скилл/реестр/файл, если можно расширить существующий.** Перед тем как
   создать что-то новое — спросить: «эта capability уже где-то живёт хотя бы как prose?» (ответ
   есть в `docs/director/capability-map.md`).
7. **Перед стартом нового среза — перечитать §1.1, §1.2 и нужную строку capability-map, а не
   восстанавливать логику по памяти.**

Это миграционный манифест: capability → где живёт сейчас → runs/prose/mixed/absent → куда

## 5. Регламент — консолидировано, самое важное первым

1. **Перед тем как редактировать/резать текст, на который что-то может ссылаться — грепни ВСЕ
   тестовые файлы на буквальную подстроку/имя документа, который трогаешь, и прогони их все.**
   `grep -rl "<буквальная фраза, которую меняешь>" tests/*.py` — дёшево, быстро, единственная
   защита, которая реально срабатывала весь день.
2. **Правки строк текста, которые «выглядят как дубль» — не факт, что дубль.** Сначала измерить
   связность (трассировка, ratchet, grep по тестам), потом резать. Честный отказ резать —
   нормальный итог.
3. **Не записывать числа «на будущее»**, если сейчас нет кода/теста, который их читает.
4. **Записи prover/skill-review — `Findings:`/`Blocking:` — значение НА СВОЕЙ СТРОКЕ**, без
   текста-продолжения там же, и БЕЗ второго случайного вхождения `^Blocking:` где-то в прозе
   записи (гейт a парсит построчно и берёт первое совпадение). Перед коммитом: `grep -c
   "^Blocking:" <файл>` должно дать `1`.
5. **Одна задача за раз, одной строкой** — что делаю и как пойму, что готово.
6. **Стоп на границе** — смежную проблему записать (см. §0.1), не чинить попутно.
7. **Адресное чтение** — grep + нужные строки, не тела документов целиком, кроме случая, когда сам
   документ — предмет правки.
8. **Широкий поиск и мехправки — воркеру**, но без долгих фоновых процессов — дочерние процессы
   гибнут вместе с воркером. Длинные проверки — только CI.
9. **Бриф воркеру/ревьюеру должен явно запрещать запускать `pytest` без явного списка файлов, и
   явно запрещать запускать `pytest` (любой) без `run_in_background: true`.**
10. **Параллельные воркеры в одном worktree — ок при непересекающихся файлах**, коммитить
    оркестратору только явными путями, не `-A`.
11. **Правка `guardrails/pre-push`/чего-то, что вызывает хук — обязательно `bash
    guardrails/install.sh` после**, иначе gate m блокирует пуш. Правка `skills/*/SKILL.md` —
    обязательно `bash scripts/sync-skills.sh` после, тем же образом. **Если тот же скилл правится
    ещё раз ПОСЛЕ того, как sync уже гонялся — гонять sync заново перед пушем.**
12. **Отчёт после каждого шага по-русски, простыми словами**, без внутренней кухни.
13. **Не верить хендоффам, включая этот, если git говорит иное.**
14. **Версия скилла — не независимый семвер, версия ОДНА на весь пакет** (`VERSION`=5.0.0,
    `tests/test_version_is_one_fact.py`, INV-178). Существенность правки покрыта gate s
    (skill-review) отдельно от номера версии.
15. **Каждый push требует ОТДЕЛЬНУЮ prover-запись (гейт a), даже когда правка кажется маленькой
    или уже покрытой предыдущей записью.**
16. **Локальную проверку масштабировать по охвату правки: узкая правка — известные целевые тесты,
    широкая — предварительно ГРЕПНУТЬ и прогнать файлы с pack-wide инвариантами** (прежде всего
    `tests/test_traceability.py`), но НЕ полный `pytest -q` (запрещён, см. §6). Признаки
    «широкой» правки: добавление/удаление/переименование структурной сущности пакета, правка
    документа, который где-то перечислен/зеркалится (ростеры, счётчики, индексы, футеры «pack,
    whole»), затронуто больше 1-2 файлов. **Это будет верно для ВСЕЙ Полосы B п.6-9** — cutover
    трогает структурную сущность пакета (build-pipeline целиком), значит широкая проверка
    обязательна, не только целевые тесты.
17. **При переносе reference-файла между скиллами — grep по ИМЕНИ ФАЙЛА не ловит тесты, которые
    проверяют его СОДЕРЖИМОЕ через `read_all`/`read_all_flat`'s `references/*.md`-глоб, не называя
    файл по пути.** Метод: вытащить уникальные фразы/подстроки из содержимого перенесённого файла
    и прогнать их по всем `tests/*.py`, проверяя, читает ли окружающий тест именно исходную (а не
    новую) поверхность скилла.
18. **Prover-запись и skill-review-запись — коммитить ОТДЕЛЬНЫМИ коммитами, не одним.**
    `guardrails/check-prover-record.sh`'s self-naming exemption проверяет только пути под
    `docs/prover/` — `docs/skill-review/` в это исключение НЕ входит. Один коммит с обеими
    записями разом не освобождается от self-naming и должен содержать свой же будущий SHA —
    невозможно до коммита. Фикс: skill-review-запись коммитить отдельно первой, получить её SHA,
    вписать этот SHA (плюс SHA содержательного коммита, плюс базовый SHA) в поле `Range:`
    prover-записи, закоммитить prover-запись последней и в одиночку.
19. **Вставка/удаление контента в SKILL.md с построчными pin-реестрами (`.live-spec/r*-rule-*.md`,
    `architecture/*.md`) сдвигает все pin'ы НИЖЕ точки правки — проверять gate g
    (`guardrails/check-pin-drift.sh`) сразу, не только тесты.** Метод: `grep -n` на точную цитату
    каждого pin'а в новом файле, обновить только диапазон/номер строки, не байты/цены/тесты.
    **Перед любой правкой SKILL.md — грепнуть `.live-spec/*.md` и `architecture/*.md` на путь
    этого файла**, чтобы узнать заранее, есть ли pin'ы ниже точки правки. **Build-pipeline теряет
    много строк в п.6 — почти гарантированно заденет чужие pin'ы, планировать этот шаг заранее.**
20. **Gate a (self-naming exemption) ловит КАЖДЫЙ раз, когда коммит трогает файл вне
    `docs/prover/`/`docs/skill-review/`/`docs/language-reads/`, даже мелкий.** Любой коммит, не
    лежащий целиком в трёх recordless-папках, обязан быть назван существующей prover-записью до
    пуша — писать её СРАЗУ после такого коммита, не откладывая на потом в надежде, что предыдущая
    запись зацепит его широким Range.
21. **Перед тем как писать добавку для "пробела" из чужой классификации — сверить его с
    `PRODUCT_SPEC.md`/`spec/*.md` на закрытый набор домов, не только с прозой скиллов.** Метод:
    `grep -rln "INV-XXX" tests/*.py`, затем прочитать сам тест на `HOMES`/`TRACKED_HOMES`-подобный
    список. Это уже неактуально для п.6 (вся классификация партии 2b завершена), но актуально,
    если в процессе удаления найдётся ещё что-то похожее на "пробел" — не доверять старой
    классификации на слово.
22. **Gate h (tests-present) требует изменения ПОД `tests/` на каждую правку "user-facing"
    skill-файла (`SKILL.md`), даже чисто текстовую.** Не отписка — реальный тест, закрывающий
    настоящий пробел (пример: `test_class_hunt.py` не проверял дом в Director, пока это не
    потребовал gate h). На п.6 build-pipeline теряет огромный объём — планировать реальные
    тестовые изменения (п.7 списка), не токен-правку ради гейта.
23. **Verbatim-совпадение с исходным текстом (5+ слов подряд) при переформулировке — ловится
    только программным n-gram-сравнением, не на глаз.** Дважды за сегодня переформулировка,
    визуально выглядевшая "явно другими словами", всё равно совпадала с исходником на 5-6 слов
    подряд после первого фикса. Метод: `python3` с set пересечением 5-грам по словам, исключая
    имена собственные/пути.
24. **Инлайн code-span (`` `path/to/file` ``), разбитый переносом строки в исходном .md-файле,
    рендерится с лишним пробелом внутри пути (CommonMark схлопывает перенос строки внутри
    code-span в пробел).** Проверять `sed -n` на сырые строки (не рендер) после любой правки,
    где code-span близко к границе строки.
25. **Параллельная работа над одним и тем же файлом (даже разными правками в разных участках) —
    риск, что один воркер/ревьюер увидит правку другого как "чужую" и попросит откатить.** Если
    2 задачи трогают один файл параллельно — либо явно разносить участки и предупреждать
    ревьюеров об этом заранее, либо не запускать параллельно. Сегодня это стоило одного лишнего
    раунда (class hunt пункт rule 14 vs A.7 компрессия того же файла).
26. **Полный `python3 -m pytest -q` гоняется ТОЛЬКО на CI, никогда локально (виснет) — значит
    локальные целевые прогоны МОГУТ пропустить широкие regression'ы, которые задевает большая
    правка структурной сущности пакета.** На Полосе B п.6 первый пуш прошёл все локальные гейты
    зелёным (гейт b/полный suite локально не проверяется в принципе), но CI нашёл 25 упавших
    тестов в ~20 файлах, которые ни один локальный целевой прогон не касался. **После любого пуша
    с широким reach (структурная правка пакета) — ОБЯЗАТЕЛЬНО проверять `gh run view` до success,
    не считать работу законченной по локально-зелёным гейтам.** Локальный push-гейт — необходимое,
    но не достаточное условие для такой правки.
27. **Тесты вида `..._in_both_homes` / с атрибутом `TRACKED_HOMES`/`HOMES` — это НАМЕРЕННЫЙ
    dual-witness паттерн (факт обязан стоять в ОБОИХ домах и они должны совпадать), а не случайный
    дубль на безопасное удаление.** Если один из домов — build-pipeline (или другой файл, который
    удаляется/сжимается), у факта нужно найти РЕАЛЬНЫЙ новый второй дом, не просто снять
    build-pipeline-часть проверки как "уже покрыто в другом месте той же функции" — если
    single-home покрытие было бы достаточно, тест не назывался бы "in_both_homes" и не носил бы
    отдельный список домов.
28. **Докстринг или имя теста вида "...'s one home is X" / "the pipeline's own step N" — это
    явное заявление, что X (или конкретная секция build-pipeline) — канонический, единственный дом
    факта, а не просто исторический артефакт того, что раньше писать было больше негде.** Такой
    сигнал — восстановить контент НА ЭТОМ САМОМ X, а не удалять его как «уже покрыто в спеке».
    Дважды за срез п.6 более ранняя классификация "already fully specced, безопасно удалить"
    оказалась неверной именно по этой причине (craft ladder, closed-set door) — spec-уровневое
    покрытие не отменяет отдельного skill-уровневого требования, если тест или докстринг явно его
    формулирует.
29. **`scripts/sync-skills.sh` нужно гонять заново КАЖДЫЙ раз, когда тот же скилл правится ПОВТОРНО
    после того, как sync уже прошёл для предыдущей правки того же среза** — не только один раз "в
    конце". Дважды за ночь push падал на `check-config-health.sh`'s drift-проверке именно из-за
    этого: правка → sync → ещё одна правка того же файла (например, по замечанию ревьюера) → push
    без повторного sync → gate m красный. Симптом в логе пуша: `{"severity":"error","code":
    "config-health","message":"installed skill drifted from source: <skill>"}`. Правило то же, что
    §5 п.11 уже формулирует для "того же скилла правится ещё раз" — но конкретно ловится не
    локальным тестом, а живым pre-push хуком, и раунд ревью между двумя правками — самый частый
    момент, где про это забывают.

## 6. Находки прошлых сессий — не чинить без отдельного решения

**Gate a ломается при push из worktree bare-репозитория** — обход, НЕ `--no-verify`:
```
cd /private/tmp/ls-director/wt
GIT_DIR="$(git rev-parse --git-dir)" GIT_WORK_TREE="$(pwd)" git push origin <branch>:main
```

**Полный локальный `pytest` в этом окружении часто виснет на 0% CPU** (зависает и не завершается
никогда), `guardrails/reap_owned_group.py` конфликтует с окружением Claude Code. Никогда не
гонять полный набор локально и без присмотра — CI гоняет на каждый push. Если запустил по
ошибке — искать и убивать вручную (`ps aux | grep pytest`).

**`tests/test_guardrails.py` делает `git stash`** и не восстанавливает при обрыве прогона —
коммитить до прогона, гонять точечно через `-k`/явный путь, никогда весь файл вслепую.

**Локальный push-гейт гоняет только быстрое подмножество тестов**, полный `pytest -q` — только
CI (`.github/workflows/gates.yml`).

**Известный, не починенный дрейф:** `spec/guardrails-freshness.md` Requirement 306 (INV-305) всё
ещё может утверждать что-то про снесённый гейт — проверить при следующем прикосновении к этому
файлу, не приоритет сам по себе.

`tiktoken` установлен в системный Python (`pip3 install tiktoken`) — не убирать, полезен для
дальнейших измерений.
